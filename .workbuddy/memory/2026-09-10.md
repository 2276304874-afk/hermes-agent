**现象**：pull 卡在 90%（8.1/9.61GB），速率 0.15~0.21 MB/s，ETA 175min，进程却活着（PID 15176）。

→ **可复用规则**：**"下载慢/卡住"先别急着换镜像或放弃；先 `curl -L` 直连测 CDN 真实带宽。若 curl 快而 pull 慢 → 杀 pull 重跑即可满速续传。** 判断进度别看 `ls -l` 的 apparent size（ollama 预分配满尺寸），要看 `stat -f %b`（allocated blocks ×512）的增量。

**结果**：`gemma4:e4b`（9.6GB，16:59:38）+ `hermes-local-gemma4:latest`（Modelfile 派生，复用同 blob 不占额外盘）均已就位。三模型基准脚本 `/tmp/bench_models.py`（task S8Y3AY）自动接力开跑，基线内存已极紧：`free=0.06 wired=8.35 compressed=3.24 | swap used 2.23GB`（加载 e4b 前就如此）。

## 17:25 三模型基准实测结果（效果 + 内存，全部模型保留未删）

**两大反直觉结论**：
1. **e4b 反而最省内存（3.3GB）**。gemma4 是 **PLE 稀疏激活**：9.6GB 权重只把活跃层常驻，其余 mmap 按需读。**"9.6GB 会吃死 16G" 的担心被推翻** —— 比 qwen3.5:9b(6.0GB)/qwen3:8b(7.9GB) 都小。
2. **e4b 解码快 4.7 倍**（39.25 vs 8.4 tok/s），16K 压测也快一倍。原以为快的 qwen3.5:9b 实际最慢。
- 注：`ollama ps` 的 SIZE 是**实际常驻内存**，不是磁盘大小；别拿磁盘尺寸判断内存压力。
- swap 全程约 used 2.0~2.3GB / total 3GB，三个模型都没爆（本机此前基线就已在用 2GB swap）。

**⚠️ 重大测试陷阱（血泪）**：`gemma4:e4b` 与 `qwen3.5:9b` 都是 **thinking 模型**，会先吐 800~1500 字思考再吐答案。基准脚本 `num_predict=200` → **思考吃光额度、`message.content` 为空**；且脚本只读 `content` 没读 `thinking` → 视觉项全部假阴性"未见 7391"。**专项复测（num_predict=1024）两者视觉均✅准确**（读出 `HERMES TEST7391` / `triangle: RED` / 红色三角形+蓝色边框）。
→ **可复用规则：测 thinking 模型的任何"内容类"能力，必须给足 num_predict 并同时读 `message.thinking`；否则会把"思考占满额度"误判成"模型不会"。** qwen3:8b 工具项 ❌ 大概率同源假阴性（num_predict=128 太小），待复测。

**结论**：**gemma4:e4b 是这台 16GB 机器的明确赢家** —— 最快、最省内存、原生工具+视觉+音频，只有冷加载慢（79.7s，热后走缓存）。UI 默认模型已指向 `hermes-local-gemma4`，`/api/models` 解析正常。

## 18:10 首 token 延迟深挖 + 开源方案调研（重要结论）

**量化拆分**（`hermes prompt-size` + ollama 日志 + 直测 oneshot）：
- 提示词 64,021B ≈ **14,513 token** = 工具 schema 37.3KB(20 工具/13 工具集) + 技能索引 13.9KB(190+ 技能×~75B) + 其他系统提示 12.8KB。
- prompt-size 的"分层"显示 **volatile 层 15.6KB > stable 层 9.8KB**（memory/profile/timestamp）。
- **直测 `hermes -z "只回复两个字"` = 25.7 秒**（绕过 UI）→ **~25s 是 Hermes 引擎每轮冷启动的固定开销**，与模型/UI 无关。日志显示每轮要 "Plugin discovery complete: 57 found, 51 enabled"。
- 模型侧：冷态 prompt eval 69.7s（前缀未缓存）；热态缓存命中仅 0.3s，剩 ~11s 生成。

**✅ 实测推翻官方说法**：Hermes issue #6839 称"tool-formatted prompts 比纯文本慢 10 倍（1230 vs 134 tok/s）"。我实测（`/tmp/tool_prefill_test.py`，e4b）：纯文本 0 工具 253 tok/s / 8 工具 355 / **20 工具 435** / 等长纯文本对照 322 → **带工具反而更快，成本纯粹线性于 token 数**。→ 所以"lazy tool loading"的收益被高估，裁工具的收益没有想象中大。

**✅ 真正的解法（重大发现）**：`hermes serve` = 常驻的 **JSON-RPC/WebSocket 后端**（"the backend server the desktop app connects to"，默认 9119），**当前没在跑**。我们的 UI 是每发一条消息就 `spawn hermes -z` 冷启一次 → 25s/条。若改为连常驻 `hermes serve`，agent 常热，**每轮开销有望从 25s 降到 1~2s**。这是最优解，且是原生能力，无需外部依赖。

**开源方案调研结论（都不如上面那条）**：
- **OpenSkills**（LingyiChen-AI/OpenSkills，Apache-2.0，真实存在，支持 Ollama）：三层 progressive disclosure（元数据/指令/资源），但它是**独立 agent 框架**，接入=换掉 Hermes 引擎 + 重写 190 技能，不划算。
- **rapidarchitect/custom-agent-with-skills**：同类（Pydantic AI），同样要换引擎。
- **microsoft/LLMLingua**（MIT，~6k star）：提示词压缩 3~20×，但①面向云端省成本，本地免费无收益；②压缩器本身是另一个小模型，16G 机器装不下；③**压不了 `tools` JSON 数组**（Ollama 要求合法 schema）。
- **headroom / lean-ctx / llmtrim / rtk / TOON**：面向云端计费或历史/轨迹压缩，不解决我们的**静态每轮开销**。
- **Cursor 的 dynamic context discovery**（官方称省 46.9%）：思路对，但 vendor-native 拿不到。
- **Hermes 官方 issue #6839**（two-pass lazy tool loading，`tools.loading: lazy`）：**未实现**；且本机 v0.21.0 的 `tool_search` 常驻配置明确写 **"Core Hermes tools … are NEVER deferred"** → 内置工具永不被懒加载，指望官方机制没用。
- 原生可用杠杆：`hermes tools disable <名字> --platform cli`（持久生效）；`-t TOOLSETS`。

**当前开启的工具集**：web/browser/terminal/file/code_execution/vision/image_gen/tts/skills/todo/memory/session_search/clarify/delegation/cronjob/computer_use（video/video_gen/x_search/stt/context_engine/homeassistant/spotify/yuanbao/a2a 已关）。可裁候选：browser(3.0KB)/code_execution(2.9KB)/delegation(3.7KB)/tts(1.8KB)/session_search(3.1KB) ≈ 省 14.5KB。
**另注**：agent.log 有 `MCP server 'format-test' failed … requires the 'mcp' Python SDK` —— 存在一个残留 MCP 配置但 SDK 没装。

## 18:30 `hermes serve` 常驻后端可行性验证（✅ 通过，量化出 400× 提升）

**启动**：`env -u PYTHONPATH ~/.hermes/venvs/hermes/bin/hermes serve --port 9119 --host 127.0.0.1 --skip-build`
（headless，uvicorn/FastAPI；`--skip-build` 因为 `web/dist` 不存在，但我们只要 API；`hermes serve --stop` 认不出手工起的进程，需按 PID kill）。

**协议（从源码读出，OpenAPI 里没有 WS）**：
- 端点 `ws://127.0.0.1:9119/api/ws`，换行分隔 JSON-RPC，与 Ink TUI / 桌面端同一套 `tui_gateway.dispatch`。
- **鉴权**：回环模式（`app.state.auth_required=False`）用 **`?token=<__HERMES_SESSION_TOKEN__>`**（token 在 `GET /` 的 HTML 里）；gated 模式才要 `?ticket=`（`POST /api/auth/ws-ticket`，单次 30s TTL）或 `?internal=`。不带 token → **HTTP 403**。
- 关键 RPC：`session.create`（1次拿 session_id+info）、`prompt.submit {session_id,text}` → 立即返 `{"status":"streaming"}`，随后推 **`message.delta` / `message.complete`**、`tool.start/progress/complete`、`approval.request/respond`、`session.*`。注意 `prompt.submit` 是**异步**的，RPC ack ≠ 轮次结束，必须继续监听事件流（我第一版脚本把 ack 当结束，误判"0 秒完成"）。
- 源码位置：`hermes_cli/web_routers/chat_ws.py`(`/api/ws`)、`tui_gateway/AGENTS.md`(协议表)、`tui_gateway/methods_prompt.py:534`(`prompt.submit`)、`hermes_cli/web_server_chat.py:209`(`_ws_auth_reason`)。

**✅ 决定性结果 —— agent 就绪成本 25.7s → 0.06s（约 400×）**：

| 环节 | `hermes -z`（现架构） | `hermes serve`（常驻） |
|---|---|---|
| agent 就绪（握手+建会话） | **25.7s**（进程级冷启） | **握手 0.05s + 建会话 0.06s** |

→ 因为 51 插件 / 190 技能 / 工具注册表**在 serve 启动时只加载一次**，每轮不再重复。
实测 3 连测：0.22s / 0.06s / 0.06s（首次略慢）。
**剩余每轮成本 ≈ 仅模型 prefill+生成**（热态约 11s）→ 预期端到端 ~11s，对比现在 37s。

**⚠️ 未完成**：真实的 prompt→首字延迟没测到干净数字，因为**另一个 WorkBuddy 会话把 `qwen3:14b`(11.4GB) 压在 GPU 上**（44 tok/s），ollama 单驻留导致我的请求排长队（一次测试 8 分钟没出首字）。**待机器空闲时复测单轮首字延迟。**

**若采纳的改造要点**：server.js 的 `handleChat` 从「`spawn hermes -z` + tail 流文件」改为「WS 连 9119、`session.create` 复用、`prompt.submit` 后转发 `message.delta`/`tool.*` 事件为现有 SSE 协议」；前端 SSE 协议可保持不变（只换后端数据源）。另外 `hermes serve` 天然解决 A4 cron（gatewayOk）与 D1 双驻留。

## 20:00 复测完成（机器空闲）+ 详细改造方案落盘

**复测条件**：机器空闲（ollama 仅 `hermes-local-gemma4` 驻留 3.25GB，无其他会话抢 GPU）。

**✅ 干净首字延迟（`/tmp/serve_first_token.py`，同一 session 冷/热两轮）**：

| 路径 | 冷首字 | 热首字（同会话第 2 轮） | 整轮（热） |
|---|---|---|---|
| 现状 `hermes -z` | 96.3s | 37.1s | — |
| `hermes serve` | **16.6s** | **0.7s** | **6.0s** |

- 冷 16.6s = 模型 prefill 8K token，**与 Hermes 无关、不可消除**；用户实际感知的热路径 **37.1s → 0.7s（约 53×）**。
- 事件计数（冷轮）：`reasoning.delta`×180 / `message.delta`×14 / `message.complete`×1。

**⚠️ 协议细节修正（血泪，两次踩坑）**：
1. WS 帧结构是 `{"jsonrpc":"2.0","method":"event","params":{"type":"<EVENT>","session_id":…,"payload":{…},"seq":N}}`。
   **事件名在 `params.type`，不在 `method`（`method` 恒为 `"event"`）**；我在解析时先取 `method` 导致永远匹配不到 `reasoning.delta` → 假"首字 N/A"。
2. **文本在 `params.payload.text`**，不是 `params.text`。
3. **终止事件是 `message.complete`，不是 `turn.complete`**（整轮测试从未出现 `turn.complete`）。
4. `thinking.delta` 是 **Hermes 自己的 UI 心跳文案**（"(⌐■_■) cogitating..." / "⏳ waiting on … 30s/60s"），**不是模型输出**，切勿当首字。

**✅ RPC 面已核实（`tui_gateway/` 源码）**：`session.create`（含 `cwd`/`model`/`provider`/`cols`/`profile`，模型覆盖是**会话级**不写全局）、`session.resume {session_id, eager_build}`、`prompt.submit {session_id,text,queued}`（异步）、`session.interrupt`、`approval.respond {session_id,choice,all,request_id}`、`config.set {key:"yolo",value:true,session_id}`（= allowDangerous 的正解）、`session.events.since`（事件回放，重连兜底）。事件全集：`message.start/delta/complete`、`reasoning.delta`、`reasoning.available`（工具预览文本）、`thinking.delta`、`tool.started/completed/failed`、`session.info/title`、`status.update`、`approval.request`、`sessions.changed/reclaimed`。

**❗新增高风险项**：`session.resume` 能否吃 `state.db` 的 stored id（`20260910_200246_236a2c` 格式）而 serve 内部 sid 是 `e1aee924` 短 runtime id —— **不验证就改会丢掉热路径收益**。实测帧里 `session.title.payload.session_id` 带的是 stored id，说明两者有映射，但 resume 接受哪个未验证。→ 方案第 1 步就是验证这个。
