## ③ 的性能回归修复（跑全套网时抓到的真回归）
- 现象：路由冒烟出现 `52 通过 / 2 失败`（跑前几轮是 54/0），失败项落在两条 KB 查询路由（`/api/kb/search`、`/api/kb`），且**再跑又全绿** → 典型的"只在某一时刻失败"。
- 根因（③ 引入）：`embedTexts` 把**整批文本塞进一个 HTTP 请求**（超时 120s）。KB 有 ~1200 块，而 kb-sync 每 30 分钟就可能改 `kb_inbox/kb_distilled` → 指纹一变即**全量重嵌** = 单请求阻塞数十秒 > 冒烟的 `-m 15` 超时 → 两条 KB 查询同时挂。
- **为什么这是真回归而不仅是测试问题**：`recallContext` 在**每个新会话**都跑 → 「KB 一变，下一次新会话的首 token 就被拖住」，正好打在本项目最在意的**首字延迟**上。
- 修法（`lib/knowledge.js`）：向量改按**块内容哈希**缓存（磁盘格式 v2 `{v:2,key,byHash}`），指纹变化时只嵌**新出现的块**（KB 是追加型增长 → 通常个位数）。外加：v1→v2 自动迁移（免"升级一次=全量重嵌一次"）、并发去重（同一次重建只跑一遍）、保存时按当前块剪枝（防哈希表无限膨胀）。
- 实测：重启后首次检索 689ms（含 v1→v2 迁移 + 落盘；406 items 塌缩成 244 个唯一向量，相同块共享向量）；**模拟 KB 内容变更后检索 313ms（修复前同场景 >15000ms）**。
- 新增 `test/kb-embed-incremental.test.js`（6 例锁 planEmbed 三条不变量）。
