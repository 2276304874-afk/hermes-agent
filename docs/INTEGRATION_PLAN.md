## 二、可接入项（按推荐顺序）

### P1 · 技能白名单治理 —— **先于一切新增** ★★★★★

- **做什么**：给 `~/.hermes/skills` 的 100 个技能做**白名单制**，只让高频技能进入 system prompt。
- **为什么第一**：唯一同时被文档警告和本机实测指向的问题。
  在 prompt 预算已经透支的情况下继续挂载新技能，只会让每一项的
  边际成本都更高、归因更难 —— **先消肿，再进补**。
- **接入点**：Hermes 侧技能加载配置 + 本机 skills 目录整理（不改本仓库代码）。
- **工作量**：⚠️ 半天；**风险低**（可回退：保留原目录副本）。
- **验收**：Hermes 日志的 `in=` 值显著下降，且常用工具仍能被正确调用。
- **依赖**：**必须最先做**，后续所有新增都要在同一预算下重新评估。

> 这与 `ACTION_PLAN` 的 T6（开启 `tool_search` 按需加载）是同一目标的两条路：
> 白名单是**静态裁剪**，`tool_search` 是**运行时按需**。推荐先白名单（简单可控），
> 效果不够再叠加 `tool_search`。

### P2 · `OpenViking` — Agent 长期记忆 MCP ★★★★☆

- **做什么**：把会话/任务历史沉淀为可检索的长期记忆。
- **为什么靠前**：本项目已有 KB 能力，但偏「文档知识库」；OpenViking 偏「Agent 自身记忆」，
  与现有 KB 定位互补（文档原文也这么说）。
- **接入点**：作为**独立 MCP 进程**接入，通过 `~/.hermes/config.yaml` 的 MCP 配置段。
- **⚠️ 硬性约束（文档明确要求）**：**按需临时启动，禁止开机常驻** —— 本机 16G，
  常驻会显著加剧 swap。必须做成"用时启动、用完即停"。
- **工作量**：⚠️ 1 天。
- **风险**：若常驻将直接冲击内存预算，务必按"临时进程"接入。

### P3 · `spec-kit` — 规格驱动开发 ★★★☆☆

- **做什么**：新功能开工前走「宪章 → 规格 → 方案 → 任务」流程。
- **为什么适合本项目**：本项目已有 `ACTION_PLAN` / `UPGRADE_ROADMAP` 等**自产规划文档**，
  与 SDD 天然契合；能减少"想到哪改到哪"造成的返工（本轮 session 中已发生多次编辑误删）。
- **接入点**：**纯工作流附件**，以技能形态放进 skills 目录，**不改任何运行时代码**。
- **工作量**：⚠️ 半天（含把现有规划文档改写成规格格式）。
- **价值**：中等但持续 —— 它改善的是开发过程而非产品能力。

### P4 · `llm_wiki` — 结构化 Wiki 知识图谱 ★★★☆☆

- **做什么**：把外部资料自动构建成知识图谱；自带 MCP + GUI，**原生支持 Ollama**。
- **为什么适合**：原生 Ollama 支持意味着**不引入云端依赖**，符合隐私红线。
- **⚠️ 许可注意**：GPL-v3，仅自用不分发则无影响。
- **接入点**：MCP 服务，与 P2 同理做临时进程。
- **工作量**：⚠️ 1 天。建议排在 P2 之后（先验证 MCP 接入链路通不通）。

### P5 · `superpowers` — 编码工作流技能包 ★★☆☆☆

- **做什么**：强制 TDD、Git 隔离工作树、两级子 Agent 代码评审。
- **⚠️ 文档自带的警告（重要）**：*"Hermes 长会话压缩会丢失引导指令"* ——
  本项目已开启 `micro_compact`，与该风险**正面相撞**。
- **建议**：**先不装**。若装，仅在大中型改动时临时启用，且需验证压缩后指令是否仍然有效。
- **工作量**：⚠️ 半天 + 验证成本较高。

### P6 · `opencode` — 专职编码子 Agent ★★☆☆☆

- **做什么**：把编码任务委派给专门的编码 Worker。
- **⚠️ 冲突点**：文档建议的搭配是 OpenCode + superpowers，而 superpowers 本身在此栈中有上述风险。
- **另外**：本机 Hermes 已经能完成全部实际编码任务，引入第二运行时 = 多一套进程占用 + 内存。
- **建议**：**暂缓**，除非出现 Hermes 明确做不好的编码场景。

### P7 · `magnitude` — 替换 Ollama 作推理底座 ★☆☆☆☆

- **做什么**：Agent 优化型推理服务器，整机内存水位感知自动卸载模型。
- **⚠️ 文档自身建议**：*"整套链路跑通稳定后再测试替换 Ollama"*。
- **判断**：**当前不满足前置条件** —— 本机链路尚有已知的 36s 延迟问题未根治，
  此时替换底座会让归因彻底失效（换底座后延迟若变化，无法判断是谁的功劳）。
- **建议**：放到最后，且必须等到 P1 完成、延迟基线稳定之后。

## 四、边界清晰 / 可插拔 / 向后兼容的机制

1. **物理隔离优于逻辑开关**。所有新增能力要么挂在独立 MCP 进程，要么挂在技能目录，
   **不进入 `lib/` 运行时主链路**。任何一项出问题，摘掉它不影响其它功能。
2. **统一走「准入门禁」而非各自接线**。新增任何技能/MCP，先过一道检查：
   本机 prompt 预算（`in=` ≤ 目标值）与内存水位。**预算不够就不准入，先减再增。**
3. **临时进程，不做常驻**。P2/P4 这类 MCP 必须是"用时起、用完停"，
   与文档"关键提醒"一致 —— 16G 机器上常驻是主要风险源。
4. **灰度与回退**：每接入一项，先记录接入前的 `in=` 与首 token 延迟基线，
   接入后立即对比。**不达标即回退**，不得带着退化继续叠加。
5. **配置与代码分离**：接入的全部是配置（config.yaml / skills 目录），
   本仓库的生产代码尽量零改动；确需改的很慢很小，且必须带测试。

## 五、P1 的低成本验证步骤（消除 §零 的假设）

在动手裁技能前，先用**一次实验**确认技能元数据到底占多少 prompt：

1. 备份：`cp -r ~/.hermes/skills ~/.hermes/skills.bak`
2. 把 skills 目录临时换成只含 5 个高频技能的精简版
3. 重启 gateway，发同一句 prompt，读 Hermes 日志的 `in=` 值
4. 恢复原目录并重启

- 若 `in=` 从 15612 大幅下降 → 假设成立，**白名单制是高杠杆手段，优先执行**
- 若几乎不变 → 大头在别处（工具定义 / 系统提示），改从 `tool_search` 入手

**这一步只需 15 分钟，能避免一整轮方向错误的返工。建议先做它。**
