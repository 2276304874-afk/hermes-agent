# 消息渠道策略（2026-09-13）

承接 `OPENCLAW-TAKEAWAYS.md` 第 5 条。这是特工与 OpenClaw **差距最大**、
也是**风险最大**的一个维度——OpenClaw 的 ClawJacked（CVE-2026-25253, CVSS 8.8）
正是从这里破的。本文给出：现状核实 → 判断 → 若做则怎么做的唯一安全路径。

---

## 一、现状（已核实）

特工现有**两个入口面**，都不是 IM 渠道：

| 入口 | 地址 | 性质 | 鉴权 |
|---|---|---|---|
| Web UI | `127.0.0.1:4173` | 人用（浏览器） | Bearer token（`~/.hermes/ui_token`） |
| gateway `api_server` | `127.0.0.1:8642` | 程序用（OpenAI 兼容 API） | Bearer key（≥16 位） |

- **零 IM 桥接**：全工程 grep `telegram|slack|discord|webhook|adapter` 只命中文档与 archive，**无任何代码**。
- gateway `platforms` 只有 `api_server` 一个键（配置第 166–171 行）。
- 配置第 164 行有明确红线注释：**「host 务必保持 127.0.0.1，切勿改 0.0.0.0（否则暴露到局域网）」**。
- UI 侧 `HOST` 默认 `127.0.0.1`，但 `lib/config.js:23` 留了口子：
  `// D4: 局域网访问设 HOST=0.0.0.0（token 认证已就位）`——**这是渠道维度最容易自伤的一步**。

对照 OpenClaw：20+ IM 适配器，每个适配器负责三件事——
**入站归一化**（平台 payload → 统一 `MsgContext`）、**出站渲染**（统一回复 → 平台格式）、
**鉴权**（验签、刷 token）；外加访问控制三件套（allowlist / DM 配对 / 群聊 mention-gating）。

---

## 二、判断：这是「刻意不做的短板」，不是「欠的债」

渠道触达是 OpenClaw 的**卖点**，对特工却是**边际价值低、风险高**的一维：

- **价值低**：特工是单人私有、local-first。你人在电脑前时，Web UI（实时流式、文件拖拽、
  检查点回滚、工作区切换）体验**远好于**任何 IM 转发。IM 的价值只在「离开电脑也要用」时兑现。
- **风险高**：渠道 = 外部不可信输入的长驻入口。OpenClaw 的 15.5 万裸奔实例、命令注入、
  SSRF、路径穿越、prompt-injection→RCE，**全部**从渠道/网关进。你当前「零出网 + loopback」
  的安全优势，一旦引入入站渠道就会**显著劣化**。
- **结论**：**除非有明确刚需（如外出时要下发任务、要手机端收推送），否则不建议做。**
  若做，**只做一个渠道，做对，别铺开**。

## 三、若做：唯一安全的接入路径（出站长轮询）

见配图。核心是**方向反转**：

```
❌ 入站 webhook 式（OpenClaw 默认形态）
   IM 平台 --主动 POST--> 你的机器:必须开入站端口/公网暴露
   → 端口可达 = 攻击面 = ClawJacked 病根

✅ 出站长轮询式（推荐）
   你的机器 --主动 GET 拉取--> IM 平台的 API（如 Telegram getUpdates / long-poll）
   → 只出站、零入站端口、防火墙后也能跑，天然绕开 ClawJacked 病根
```

### 适配器接口（先抽象，再实现）

参照 OpenClaw 的三职责，但**只在自己代码里抽象一个最小接口**：

```
normalizeInbound(platformMsg) -> { senderId, text, attachments, threadId }
renderOutbound(reply)         -> platformMsg
verifyAuth()                  -> 由长轮询的 token 保证（出站方向无入站 webhook 验签问题）
```

### 必须内置的闸门（缺一不可）

1. **发送者白名单**：只有预登记的 `senderId` 被处理，其余一律丢弃（不是「友好拒绝」，是**静默丢弃 + 记日志**）。
2. **首次配对**：未知发送者首次出现 → 生成一次性配对码，需在本机 Web UI 确认后才加入白名单。
3. **危险操作不放宽**：渠道来的消息**照样**走现有三色权限 + safety hook + 检查点，
   绝不因「来自 IM」而降级。allowDangerous 只能由本机 Web UI 授予。
4. **会话映射**：一个 (渠道, 对方 ID) ↔ 一个 gateway session，写入 `active` 表时**顺带上第 2 条
   （会话车道）的并发守卫**，否则 IM 侧连发两条照样踩同一个竞态。
5. **附件隔离**：抓下来的媒体文件走现有 `media.js` 上传加固（`..`/绝对路径/边界/文件名清洗四层），
   落到独立目录，不进工作区根。

### 分阶段路线（若决定做）

| 阶段 | 内容 | 成本 |
|---|---|---|
| 0 | 抽象 `ChannelAdapter` 接口 + 白名单/配对存储 | 小 |
| 1 | Telegram 适配器（long-poll，无入站端口）——**只做一个** | 中 |
| 2 | 会话映射 + 并发守卫（复用第 2 条会话车道） | 小 |
| 3 | （可选）飞书/钉钉——仅当确有该平台刚需**且**支持 long-poll/IM 主动连接 | 每平台独立评估 |

### 阶段 0 已落地（2026-09-13，用户决定：只预留接口，不接渠道）

`lib/channel.js` 已实现**契约 + 注册表 + 参考适配器**，**未接任何 live 路径**（`/api/chat` 仍走原逻辑）。
刻意不做接线：没有真实渠道消费者时改热路径 = 纯风险，等真有需求再由真实需求驱动。

关键设计：**把上面这些安全决策编码进契约**，而不是写在注释里等人自觉。
`assertAdapter()` 在**注册那一刻**就拒掉三类违规适配器：

1. `inbound !== 'pull'` → 拒绝。webhook/push 式要开入站端口，正是 ClawJacked 病根；
2. `mayGrantDangerous === true` → 拒绝。危险操作只能由本机 Web UI 授予；
3. 缺任一必需闸门（`REQUIRED_GATES`：allowlist / firstPairing / dangerousNotRelaxed /
   sessionLaneGuard / attachmentIsolation）→ 拒绝，且错误信息点名缺哪一条。

于是「想接一个不安全的渠道」会在**注册期**失败，而不是等线上出事。
参考适配器 `webAdapter`（把本机 Web UI 当第一个渠道）存在的意义是证明契约可实现，
并给将来真正的渠道一个照抄模板 —— 由 `test/channel.test.js` 12 条用例覆盖。

> ⚠️ **绝不引入**：开放技能市集、要求公网入站端口的 webhook 式接入、
> 「为方便先开 0.0.0.0 再说」。这三条中任意一条，都会把你已建立的
> 「零出网 + loopback」安全优势抹平。

## 四、立即要守的边界（无论做不做渠道）

1. **UI `HOST` 保持 `127.0.0.1`**。`lib/config.js:23` 的 `0.0.0.0` 口子仅在你
   **明确**需要局域网访问时开，且开之前确认 Bearer token 已强制（现状已就位），
   并评估同网段设备可信度。**默认永不改**。
2. **gateway `host` 保持 `127.0.0.1`**（配置第 164 行红线，已有注释锁死）。
3. 任何新增入口（渠道/工具/端口）都必须先过一遍
   `OPENCLAW-VS-HERMES-2026-09-13.md` 的 CVE 对照清单。

---

## 一句话结论

**渠道是它最强的一维，也是你安全优势最容易被它拖平的一维。**
对单人 local-first 场景，**默认不做**是对的；若确有刚需，就按上面的
**出站长轮询 + 白名单/配对 + 危险操作不放宽**做，**一次只加一个渠道**。
你现有的 gateway 会话链路与三色权限可直接复用——需要新写的只有「适配器 + 闸门」这一薄层。
