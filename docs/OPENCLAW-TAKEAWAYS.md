### ⑥ 的取舍说明（为何默认关 + 加固守）

用户可选项，本机（16G 统一内存）的关键约束是**同时只容得下一个 ≥8B 模型驻留**
（gemma4:e4b 9.5G / qwen3:8b 7.4G，双驻 ≈17G > 16G → swap）。于是：

- 若降级到**未驻留**的备用模型 → 先驱逐主模型再冷加载备用 → 这一轮更慢，下一轮还得再冷加载主模型。
  **代价大于原地等**。故 `fallbackResident === false` 一律不降（硬守卫）。
- **只在首 token 之前**降级：已吐字再换模型，用户看到两段拼接的回答，比卡住更糟。
- 只降一级（`attempts >= 1` 即止），避免在坏模型间来回弹跳。

结论：这是一条**只在该场景刚好成立时才收益**的保险，故默认关、不配置即零影响。

### ③ 的性能回归（自引入，已修）

跑全套回归网时抓到：路由冒烟出现 `52/2`（失败项正是两条 KB 查询路由），**再跑又全绿** —— 典型「只在某一时刻失败」。

- **根因**：`embedTexts` 把整批文本塞进**一个** HTTP 请求（超时 120s）。KB ~1200 块，
  而 kb-sync 每 30 分钟就可能改 `kb_inbox`/`kb_distilled` → 指纹一变即**全量重嵌** =
  单请求阻塞数十秒，超过冒烟的 `-m 15` 超时。
- **为什么是真回归而不只是测试问题**：`recallContext` 在**每个新会话**都会跑 →
  「KB 一变，下一次新会话的首 token 就被拖住」，正好打在本项目最在意的**首字延迟**上。
- **修法**（`lib/knowledge.js`）：向量改按**块内容哈希**缓存（磁盘格式 v2 `{v:2,key,byHash}`），
  指纹变化时只嵌**新出现的块**（KB 是追加型增长 → 通常个位数）。附带：v1→v2 自动迁移
  （免「升级一次 = 全量重嵌一次」）、并发去重、保存时按当前块剪枝（防哈希表无限膨胀）。
- **实测**：重启后首次检索 689ms（含迁移+落盘；406 items 塌缩成 244 个唯一向量，相同块共享向量）；
  **KB 内容变更后检索 313ms（修复前同场景 >15000ms）**。测试 `test/kb-embed-incremental.test.js`。

## 一、立即做（3 项，低成本高回报）

### 1. 技能 eligibility 过滤 —— 直击你已知的缓存痛点 ★最高 ✅ 已完成（前提已修正）

| | |
|---|---|
| **OpenClaw 做法** | `SKILL.md` frontmatter 声明 `requires: { env: [...], bins: [...] }`；运行前按「二进制在不在、env 有没有、平台是否匹配」**过滤**，只把**合格技能**注入，且只有当前轮相关的技能注入全文（先用 name+description 匹配）。 |
| **特工现状** | `lib/skills.js` 的 `scanLocalSkills()` 无条件扫全部技能；引擎索引对全部 192 个技能注入 `name + description`（~3750 token，占 system 约 24%）。 |
| **差距** | 你已知「索引占 system 24%、命中率瓶颈是 description 质量」。但**索引里混着一批环境根本用不了的技能**（依赖未安装的二进制、未配置的云 key、非本平台），它们占着 token 却永远不会命中。 |
| **价值** | 过滤掉不可用技能 → 索引瘦身 → prompt cache 前缀更短更稳（前缀一变 cache 即失效，这是你实测过的 3.2× 首字延迟杠杆）。 |
| **落地** | ① 给技能 `SKILL.md` 补 `requires` frontmatter；② 在索引构建前做一次 eligibility 过滤；③ 急就章版：先维护一个「环境不可用技能」黑名单，索引时剔除。 |

### 2. 会话车道串行化 —— 你**真缺**，且有实际竞态

| | |
|---|---|
| **OpenClaw 做法** | per-session FIFO 车道队列，默认**同一会话只有一个 active run**，避免上下文错乱/工具状态不一致。 |
| **特工现状** | `lib/routes/chat.js` 的 `active.set(sessionId, child)`（227 / 256 / 305 / 354 行）**无任何守卫**。同一会话发第二条消息 → 直接覆盖第一条的映射。 |
| **差距（实锤）** | 后果有二：① 第一条子进程变孤儿，无人追踪；② `/api/stop` 按 sessionId 查 → 只能杀到**最新**那条，旧的那条杀不掉。这是真实竞态，不是理论风险。 |
| **落地** | 在 `handleChat` / `handleChatGateway` 入口检查 `active.has(sessionId)`：已有在跑 → 返回 409「该会话正在执行中」，或入队串行。改动小、边界清晰。 |

### 3. KB 接上向量混合检索 —— 基础设施你都有，只是没接线

| | |
|---|---|
| **OpenClaw 做法** | 记忆检索用**混合**：向量语义搜索 + SQLite FTS5 关键词，两路合并。 |
| **特工现状** | `lib/knowledge.js` 的 `recallHits()` 是**纯 FTS5 trigram**（注释已确认「检索委托给 kb/kb.py recall（FTS5 trigram）」）；而 `lib/skills.js` 才是 bge-m3 **向量**检索。**两套机制各管一摊，没有合流**。 |
| **差距** | trigram 对中文**两字词**几乎无效（需 ≥3 字符才成一个 trigram），同义异词（「写爬虫」vs「抓网页」）召不回。你的 KB 恰恰是中文为主。 |
| **价值** | `embedTexts` / `cosine` 已经现成（skills.js 里跑着 bge-m3，本地常驻）。把它复用到 KB recall = **低成本混合检索**，无需新依赖。 |
| **落地** | 在 `kb.py recall` 增一条向量通道，或干脆在 Node 侧并行跑 FTS5 + 向量、按分数合并。 |

## 二、规划（2 项，收益明确但要设计）

### 4. 压缩前自动记忆沉淀（Auto Memory Flush）

- **OpenClaw**：在 context 压缩前触发一次**静默 agentic turn**（不通知用户），提醒模型把重要信息写进记忆文件，防长对话丢上下文。
- **特工现状**：靠「人（智能体）自觉」写 `.workbuddy/memory/`，没有自动化触发点。
- **落地**：在**压缩 / 检查点回滚前**挂一个 hook，自动 flush 一次记忆。注意与你的 `micro_compact` 策略协同——压缩本身会破 prompt cache，flush 要搭在「本来就要压缩」的时机上，别新增无谓压缩。

### 5. 渠道适配抽象层（为触达扩展预留）

- **OpenClaw**：`ChannelAdapter` 三职责——**入站归一化**（各平台 payload → 统一 `MsgContext`）/ **出站渲染**（统一回复 → 平台格式，如 Slack blocks、Telegram keyboard）/ **鉴权**（验签、刷 token）。新增渠道不改核心，只加插件。
- **特工现状**：仅 Web UI 一个入口，无抽象层。
- **落地**：若将来接 Telegram / Webhook，**先抽象一个 adapter 接口**（`normalizeInbound` / `renderOutbound` / `verifyAuth`），核心逻辑只对统一结构干活。
- ⚠️ **只学抽象，别学开放市集**——技能坚持自托管 + 白名单（见第五节）。

## 三、可选（1 项）

### 6. 模型 stall 降级（Model Failover）

- **OpenClaw**：限流 / 失败时**自动切 provider**。
- **特工现状**：本地单模型；冷加载或显存争抢时会卡住（已加 `notice` + 首 token 看门狗**缓解**，但只是告知，没有**降级**）。
- **落地**：主模型 stall > N 秒 → 自动切到更小的常驻模型（如 qwen3:8b，8B 是 16G 下的安全甜点）继续本轮，而不是干等。属于「接住极端尾巴」，非必需。
